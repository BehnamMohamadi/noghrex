# تحویل فاز ۱ نقرکس — بک‌اند قابل تست

ساختار پروژه سه فاز دارد: ۱) بک‌اند، ۲) پنل مدیریت، ۳) فرانت‌اند.
این تحویل مربوط به بک‌اند است و شامل پنل یا صفحات مشتری نیست.

## محدوده این نسخه

### ۱-۱ — نقرکس آنلاین

- قیمت خرید و فروش مستقل و تاریخچه قیمت دستی.
- هر ۱۰۰۰ واحد صحیح X برابر یک گرم؛ Quote با اعتبار قابل تنظیم، بدون رزرو.
- خرید و فروش اتمیک، کنترل موجودی، مصرف یک‌باره Quote و دفتر ثبت تراکنش‌ها.
- بودجه بازخرید مستقل با تخصیص مدیر، دلیل، سابقه و حسابداری.
- گزارش جداگانه خرید/فروش، مقدار X و گرم، اصل مبلغ، کمیسیون و مبلغ خالص.
- محاسبه پول با نسبت‌های صحیح و گرد کردن رو به پایین در هر مرحله.

### ۱-۲ — فروشگاه نقرکس

- محصول، SKU، وزن، تصاویر به‌صورت URL، دسته به‌صورت متن، قیمت‌گذاری standard/custom.
- در standard، اجرت/سود/مالیات از تنظیمات عمومی physical خوانده می‌شود؛ در custom از خود محصول.
- موجودی فیزیکی و تاریخچه مستقل از موجودی X؛ کالا با موجودی صفر قابل خرید نهایی نیست.
- سبد خرید، آدرس‌ها، روش ارسال و محدودیت استان، هزینه و ارسال رایگان.
- Checkout با Snapshot قیمت و آدرس و مهلت قابل تنظیم؛ بدون رزرو موجودی.
- سفارش کیف پولی و پرداخت مستقیم آزمایشی درگاه.
- اعتبار قیمت تا پایان Checkout برای شروع پرداخت؛ پس از شروع پرداخت مهلت paymentTtlSeconds برقرار است.
- پرداخت موفق بدون موجودی یا پرداخت دیرهنگام به manual_review می‌رود؛ هیچ بخشی از سبد ناقص مصرف نمی‌شود.
- تأمین سفارش بررسی دستی، کنترل ترتیب confirmed → processing → shipped → delivered.
- لغو سفارش پرداخت‌نشده، درخواست/تأیید/رد/تکمیل بازپرداخت کامل.
- سبدی که پس از تهیه سفارش تغییر کرده، هنگام پرداخت پاک نمی‌شود.

### زیرساخت مشترک

- ثبت‌نام OTP، ورود رمز عبور، کوکی HttpOnly، JWT، خروج با ابطال نشست‌ها.
- OTP توسعه فقط در ترمینال چاپ می‌شود؛ هش کد و توکن یک‌بارمصرف ذخیره می‌شوند.
- KYC و تأیید حساب بانکی توسط مدیر؛ سقف حساب بانکی قابل تنظیم.
- کیف پول تومان/X با available و locked، Ledger، Audit و گزارش مدیر.
- شارژ درگاهی آزمایشی، کارت‌به‌کارت و شبا با تأیید مدیر.
- برداشت با قفل وجه، تأیید/پردازش/ثبت انتقال بانکی و آزادسازی در رد یا شکست قطعی انتقال.
- سقف‌های واریز/برداشت و جلوگیری از عبور هم‌زمان از سقف روزانه.
- مدیریت وضعیت کاربران، غیرفعال‌سازی بدون حذف سوابق و گزارش تراکنش‌ها.
- فهرست‌های پررکورد دارای page/limit هستند؛ limit حداکثر ۱۰۰ است.

## تصمیم‌های این تحویل

1. همه بازپرداخت‌ها، حتی خرید مستقیم با درگاه، به کیف پول تومانی نقرکس برمی‌گردند؛ برداشت بانکی جداست.
2. بازپرداخت فعلاً کامل و برابر totalAmount ثبت‌شده سفارش، شامل هزینه ارسال است. بازپرداخت جزئی در این نسخه نیست.
3. سفارش ارسال‌شده برای تکمیل بازپرداخت نیاز به تأیید دریافت مرجوعی با stockReturned=true دارد. موجودی مصرف‌شده یک بار برمی‌گردد.
4. درخواست بازپرداخت در حال بررسی/تأیید، ارسال سفارش را متوقف می‌کند. رد درخواست این توقف را برمی‌دارد.
5. پول فروش نقره و کمیسیون، خودکار بودجه بازخرید را شارژ نمی‌کنند. جزئیات در buyback-budget.md آمده است.
6. KYC آنلاین طبق مستند اولیه اجباری نشده؛ برداشت نیازمند حساب بانکی تأییدشده متعلق به کاربر است.
7. درگاه واقعی، پیامک واقعی و ارائه‌دهنده قیمت هنوز انتخاب نشده‌اند. مطابق تصمیم شما، درگاه این تحویل mock، پیامک console و قیمت دستی است. mock در production غیرفعال است.
8. برداشت بانکی توسط این نسخه خودکار انجام نمی‌شود؛ مدیر پس از انتقال واقعی، شماره پیگیری را ثبت می‌کند. مسیر fail فقط برای شکست قطعی انتقال است، نه نتیجه نامعلوم بانک.
9. یک تلاش پرداخت برای هر درخواست واریز یا سفارش ثبت می‌شود؛ شروع مجدد همان درخواست، همان Payment را برمی‌گرداند. برای پرداخت جدید پس از شکست، درخواست/Checkout جدید بسازید.
10. سهم سقف روزانه واریز هنگام ساخت درخواست ثبت می‌شود؛ درخواست‌های pending/processing/completed همان روز در آن شمرده می‌شوند. سقف روزانه بر اساس روز ایران است.

## اجرای محلی

Node و MongoDB باید نصب باشند. مسیر mongod به‌صورت خودکار روی این دستگاه پیدا می‌شود؛ روی دستگاه دیگر می‌توان MONGOD_BINARY را تنظیم کرد.

```powershell
npm install
npm run seed:local
npm run dev:local
```

برای اجرای بدون nodemon، ابتدا `npm run db:local` و سپس `npm start` را اجرا کنید.
اگر سرور از قبل روی پورت ۳۰۰۰ فعال است، نمونه دوم اجرا نکنید.

دیتابیس این پروژه:

```text
mongodb://127.0.0.1:27031/noghrex_local?replicaSet=noghrexLocal
```

اطلاعات محلی در `.local/mongodb` نگهداری می‌شود. اسکریپت، MongoDB موجود روی پورت ۲۷۰۱۷ را تغییر نمی‌دهد.
فایل `.env` از قبل ساخته شده و کلید JWT تصادفی دارد؛ `.env` و `.local` در Git نادیده گرفته می‌شوند.

| حساب تست محلی | شماره | رمز حساب تازه‌ساخته‌شده |
| --- | --- | --- |
| مدیر | 09120000001 | NoghrexLocal!2026 |
| کاربر | 09120000002 | NoghrexLocal!2026 |

اسکریپت seed رمز یا نقش حساب موجود را بازنویسی نمی‌کند و موجودی مالی تزریق نمی‌کند.
این حساب‌ها فقط متعلق به دیتابیس توسعه هستند؛ آماده‌سازی حساب مدیر واقعی جزو استقرار است.

## فایل‌های Postman

- `postman/NOGHREX-Local.postman_environment.json`: محیط محلی.
- `postman/NOGHREX-Smoke.postman_collection.json`: سناریوی ترتیبی ۴۹درخواستی قابل Run.
- `postman/NOGHREX-Phase1.postman_collection.json`: مرجع کامل API با ۱۱۲ درخواست نمونه.

### ترتیب تست پیشنهادی

1. هر سه فایل JSON را Import کنید و محیط **NOGHREX Local (test only)** را انتخاب کنید.
2. سرور را اجرا و Health را بررسی کنید: `http://127.0.0.1:3000/api/health`.
3. مجموعه **Runnable Smoke** را با Collection Runner از ابتدا اجرا کنید.
4. Loginها توکن مدیر/کاربر را از Set-Cookie استخراج و در متغیر محیط ذخیره می‌کنند. درخواست‌های بعدی از Bearer استفاده می‌کنند؛ Cookie Jar عمداً غیرفعال است.
5. متغیرهای شناسه محصول، سفارش، Quote، Payment، بازپرداخت و حساب بانکی خودکار پر می‌شوند.
6. نتیجه را در Test Results ببینید؛ Smoke شامل شارژ، معامله خرید/فروش، سفارش کیف پولی، سفارش درگاهی، بازپرداخت هر دو و برداشت است.
7. برای تست جداگانه مسیرهای دیگر، از مجموعه مرجع استفاده کنید. تأیید/رد و روش‌های پرداخت، سناریوهای جایگزین‌اند؛ کل مرجع را پشت سر هم Run نکنید.

برای تکرار کامل Smoke، runId، cardNumber و iban را خالی کنید تا مقدار جدید تولید شود.
Smoke داده آزمایشی ایجاد می‌کند و موجودی آزمایشی را تغییر می‌دهد؛ اطلاعات را پاک نمی‌کند.
بعد از سه حساب بانکی فعال، باید یکی از حساب‌های تست قبلی را با DELETE غیرفعال کنید.
متغیر ledgerId یا alertId را هنگام تست جزئی از خروجی فهرست متناظر بردارید.
برای OTP از شماره جدید signupPhone استفاده کنید و کد چاپ‌شده در ترمینال را در otpCode بگذارید.

### کلید جلوگیری از اجرای تکراری

ساخت واریز، برداشت و تغییر دستی موجودی/بودجه به idempotencyKey نیاز دارد.
برای تکرار همان درخواست، همان کلید و همان بدنه را بفرستید. برای عملیات جدید، کلید جدید بسازید.
خرید/فروش بر اساس quoteId، سفارش بر اساس checkoutSessionId و پرداخت/بازپرداخت بر اساس شناسه خودشان یک‌بار اجرا می‌شوند.
درخواست تکراری بعضی تغییر وضعیت‌های مدیریتی ممکن است 409 بدهد؛ وجه یا موجودی دوباره تغییر نمی‌کند.

### پاسخ‌ها

پاسخ موفق `status: success` و `data` دارد. فهرست صفحه‌بندی‌شده دارای
`items`, `page`, `perPage`, `total`, `totalPages` است؛ بعضی مسیرهای قدیمی آن را داخل
`data.orders`, `data.deposits`, `data.withdrawals`, `data.products`, `data.requests` یا `data.bankAccounts` قرار می‌دهند.
خطا دارای `code` و `message` است. نمونه‌های مهم:

- `AUTH_REQUIRED` / `FORBIDDEN`: ورود یا نقش نامعتبر.
- `VALIDATION_ERROR`: ورودی یا شناسه نامعتبر.
- `IDEMPOTENCY_CONFLICT`: استفاده مجدد از کلید با داده متفاوت.
- `INSUFFICIENT_BUYBACK_BUDGET`: بودجه مستقل کافی نیست.
- `PHYSICAL_INVENTORY_CHANGED`: موجودی یکی از کالاها کافی نیست.
- `INVALID_ORDER_TRANSITION`: ترتیب وضعیت سفارش رعایت نشده.
- `RETURN_RECEIPT_REQUIRED`: دریافت کالای مرجوعی هنوز تأیید نشده.

## آزمون و محدوده اطمینان

```powershell
npm test
npm run postman:build
```

تست‌ها MongoDB replica set مستقل و موقت می‌سازند و به دیتابیس محلی شما متصل نمی‌شوند.
علاوه بر تست سرویس‌ها، درخواست‌های همان فایل Smoke و اسکریپت‌های تست آن از طریق HTTP اجرا می‌شوند.
این اجرا، اعتبارسنجی خودکار API و فایل Postman است؛ اجرای رابط گرافیکی برنامه Postman نیست.

## داده‌های نسخه قبلی

این تحویل دیتابیس محلی تازه و جدا دارد. سوابق قدیمی را حذف یا مهاجرت نکرده است.
اگر دیتابیس قبلی داده واقعی دارد، قبل از اتصال آن باید تطبیق مانده مالی و مهاجرت ایندکس‌ها انجام شود:
OTP اکنون برای هر شماره/هدف یکتا است؛ Payment دارای ایندکس‌های partial برای authority/referenceId و ارتباط یکتای سفارش/واریز است؛
Order برای Checkout یکتا است و expiresAt دارد. اسکریپت توسعه این تغییرات را روی دیتابیس قدیمی اعمال نمی‌کند.

اتصال ارائه‌دهندگان واقعی و ارزیابی استقرار production پس از انتخاب سرویس‌ها انجام می‌شود؛ این نسخه برای بررسی فاز ۱ با سرویس آزمایشی تحویل داده شده است.
