# بودجه مستقل بازخرید نقره

## قواعد تأییدشده

- افزایش بودجه بازخرید فقط با تخصیص صریح مدیر انجام می‌شود؛ کاهش دستی آن نیز ثبت مدیر می‌خواهد.
- شارژ کیف پول و فروش نقره به کاربر، این بودجه را افزایش نمی‌دهند.
- فروش کاربر به نقرکس، به اندازه مبلغ خالص دریافتی کاربر از بودجه کم می‌کند.
- اصل معامله، کمیسیون و مبلغ نهایی جدا ثبت و گزارش می‌شوند. کمیسیون، سود خالص کسب‌وکار نیست.
- تمام مقادیر پول تومان صحیح هستند؛ هر ۱۰۰۰ واحد X برابر یک گرم است.

## تفکیک موجودی و حساب‌ها

`PlatformBalance.buybackAvailableToman` بودجه آزاد بازخرید است.
`PlatformBalance.tomanAvailable` موجودی تسویه برای برداشت‌های کیف پول است.
این دو موجودی جدا هستند و نباید برای محاسبه ظرفیت بازخرید با هم جمع شوند.

تأیید واریز، موجودی تسویه را افزایش می‌دهد. خرید X با کیف پول، موجودی تسویه
را دوباره افزایش نمی‌دهد؛ پول قبلاً هنگام واریز ثبت شده است.
فروش X توسط کاربر، مبلغ خالص را از بودجه بازخرید به موجودی تسویه منتقل می‌کند
و همان مبلغ را به کیف پول کاربر اضافه می‌کند. برداشت بعدی فقط از موجودی تسویه
کم می‌شود؛ بودجه بازخرید دوباره کسر نمی‌شود.

تخصیص مدیر ثبت منابعی است که قبلاً برای این منظور کنار گذاشته شده‌اند؛ این API
انتقال بانکی انجام نمی‌دهد و به‌طور خودکار از موجودی تسویه یا درآمد فروش برداشت نمی‌کند.
مدیر باید تأمین واقعی این منابع را قبل از ثبت تخصیص بررسی کند.

## ثبت حسابداری معاملات جدید

حساب‌های جدید از همان LedgerAccount و شاخص یکتای موجود استفاده می‌کنند:

| حساب | کاربرد |
| --- | --- |
| silver_sales | مبلغ اصل فروش نقرکس به کاربر |
| silver_purchases | مبلغ ناخالص خرید نقرکس از کاربر |
| buy_commission | کمیسیون خرید کاربر |
| sell_commission | کمیسیون فروش کاربر |
| buyback_budget | تخصیص‌ها منهای مبلغ خالص بازخریدها |
| buyback_settlement | منابع آزادشده از بودجه برای تسویه کیف پول کاربران |
| treasury_allocation | طرف مقابل تخصیص یا بازپس‌گیری دستی بودجه |

در خرید کاربر: بدهکار کیف پول = بستانکار اصل فروش + بستانکار کمیسیون خرید.
در فروش کاربر: بدهکار اصل خرید = بستانکار کیف پول + بستانکار کمیسیون فروش.
انتقال منابع بازخرید نیز با یک جفت ردیف جدا در همان تراکنش ثبت می‌شود:
بدهکار بودجه بازخرید، بستانکار منابع تسویه، به مبلغ خالص.
این جفت ردیف درآمد یا معامله دوم نیست و نباید به گزارش حجم معاملات اضافه شود.
ردیف‌های انتقال X همچنان جدا و متوازن هستند. برای کمیسیون صفر ردیف صفر ثبت نمی‌شود.

نمونه: اصل معامله ۱۰۰٬۰۰۰ و کمیسیون ۱٬۰۰۰ تومان.
در خرید کاربر، ۱۰۱٬۰۰۰ تومان از کیف پول کم می‌شود و بودجه بازخرید ثابت می‌ماند.
در فروش کاربر، ۹۹٬۰۰۰ تومان به کیف پول و موجودی تسویه اضافه و از بودجه کم می‌شود؛
اصل خرید ۱۰۰٬۰۰۰ و کمیسیون فروش ۱٬۰۰۰ تومان گزارش می‌شوند.

## API مدیر

- `GET /api/admin/buyback-budget`: موجودی مستقل، با کلید `availableToman`.
- `POST /api/admin/buyback-budget/adjustments`: تخصیص یا کاهش اتمیک.
- `GET /api/admin/buyback-budget/adjustments?page=1&limit=50`: تاریخچه تخصیص مدیر.
- `GET /api/admin/silver/online/trades/summary`: جمع معاملات تکمیل‌شده در هر دو سمت.

بدنه ثبت تخصیص:

```json
{
  "type": "increase",
  "amountToman": 10000000,
  "reason": "تخصیص سرمایه بازخرید",
  "idempotencyKey": "buyback-allocation-0001"
}
```

`decrease` فقط تا سقف بودجه آزاد مجاز است. هر درخواست، شناسه مدیر، دلیل، زمان،
موجودی قبل و بعد، سند حسابداری و Audit دارد. تکرار همان کلید و محتوا همان نتیجه
را برمی‌گرداند؛ تغییر محتوا یا مدیر با همان کلید خطای `IDEMPOTENCY_CONFLICT` دارد.

کلیدهای گزارش `buy` و `sell` برای سازگاری با API قبلی از دید کاربر باقی مانده‌اند:

- `buy.platformSide = sale_to_user`: فروش نقرکس به کاربر.
- `sell.platformSide = purchase_from_user`: خرید نقرکس از کاربر.

هر سمت شامل `count`, `xAmount`, `grams`, `grossToman`, `commissionToman`, `finalToman` است.
سمت بدون معامله با صفر برمی‌گردد. X واحد اصلی محاسبه است و grams برای نمایش است.
این گزارش از Trade ساخته می‌شود تا تراکنش‌های تخصیص و انتقال منابع، حجم فروش را دو برابر نکنند.

## داده‌های قبلی و راه‌اندازی

بودجه جدید پیش‌فرض صفر است؛ موجودی قدیمی به‌طور خودکار بودجه بازخرید فرض نمی‌شود.
سوابق Ledger بازنویسی نمی‌شوند؛ معاملات جدید `metadata.accountingVersion = 2` دارند.
گزارش Trade همچنان معاملات تکمیل‌شده قدیمی را نیز شامل می‌شود، ولی تفکیک حساب‌های جدید
فقط از زمان این تغییر برقرار است. اگر قبلاً تراکنش واقعی ثبت شده، موجودی تسویه قدیمی
باید پیش از بهره‌برداری با بانک و تعهدات کیف پول تطبیق داده شود؛ این تغییر، مانده‌های
تاریخی را به‌صورت حدسی اصلاح نمی‌کند.

## آزمون

`npm test` یک MongoDB replica set موقت روی پورت آزاد و مسیر موقت جدا راه‌اندازی
می‌کند و به دیتابیس پروژه متصل نمی‌شود. `mongod` باید نصب باشد؛ در صورت نیاز
مسیر فایل اجرایی را با `MONGOD_BINARY` مشخص کنید. آزمون‌ها تفکیک بودجه، کمیسیون،
برداشت، بازگشت کامل تراکنش ناموفق، درخواست تکراری و رقابت هم‌زمان را بررسی می‌کنند.
